# use-formio — interactive docs (example app)

The live docs site for `use-formio`: <http://use-formio.svehlik.eu>

It is a [Vite](https://vite.dev) + React 19 + TypeScript single page app that renders every
example twice — once as a **live, interactive form** and once as its **source code** — so the
snippet a reader copies is byte-for-byte the file that produced the demo next to it.

## Running it

```bash
cd example
npm install
npm run dev     # http://localhost:1234
npm run build   # static site in example/dist
npm run preview # serve example/dist
npm run ts:check-types
```

Requires Node >= 20.19 (developed on Node 26).

## How it is wired

- **The library is imported from source, not from `dist`.** Every example imports
  `from "../../src"`, so the docs always exercise the code that is currently in the repo — there
  is no build step to forget. `vite.config.ts` sets `server.fs.allow` so the parent `../src`
  directory can be served, and `resolve.dedupe` so `../src` and the app share one React instance.
- **Snippets come from `?raw` imports, highlighted at build time.** `exampleSources.ts` imports
  every `./examples/*.tsx?raw`, and the `highlightExampleSources` plugin in `vite.config.ts`
  rewrites each of those modules: it lightly edits the source for display (`"../../src"` becomes
  `"use-formio"`, the docs-only `<DEBUG_FormWrapper>` wrapper is stripped) and then runs
  [shiki](https://shiki.style) over it with the `tsx` grammar and two themes, so what reaches the
  browser is `{ html, palette }`: finished `<span class="c…">` markup plus the ~20 colour classes
  it uses (each class carries `--shiki-light` / `--shiki-dark`, the stylesheet picks one per page
  theme; `raw-snippets.d.ts` types the module). This replaced the old `regenerate-examples.js`
  codegen script and the `__generated_examples__/` directory it produced (which had to be
  regenerated by hand and silently went stale), and later a `highlight.js` pass that only had a
  `typescript` grammar and left all JSX uncoloured.
- **Syntax highlighting never runs in the browser.** shiki is a *build time only* dependency:
  the snippets are highlighted by the vite plugin above, and the JSON state dumps by the ~40 line
  `highlightJson.ts` tokeniser (`hljs-*` class names, coloured by the same tokens as the
  snippets). `CodeBlock.tsx` only sets the finished markup. See `PERF.md` for why - a highlighter
  in the browser was the single most expensive thing on the page.
- **Layout and visual identity** are hand-written CSS in `styles/` (`tokens.css` for the light/dark
  palette and type scale, `base.css`, `chrome.css` for the top bar, hero, sidebar and footer,
  `example.css` for the demo / state / source composition). There is no CSS framework; the design
  plan is in `DESIGN.md`. Page chrome components: `Hero.tsx`, `Toc.tsx`, `SourcePane.tsx`,
  `CopyButton.tsx`, `ThemeToggle.tsx`, `Footer.tsx`.
- `DEBUG_FormWrapper.tsx` renders the live form state as JSON next to each demo. It is docs-only
  chrome and is stripped from the displayed snippets. It re-renders on every keystroke, so the
  dump is isolated behind `React.memo` keyed by the serialised JSON.
- **Performance.** Every example section is a `React.memo`'d `ListItem`, the layout reads the
  viewport through one shared `useShowCodeRight()` store, and the 18 code columns are mounted in
  a `startTransition` so they never block the first paint. `PERF.md` documents the measurements,
  and `e2e/perf.spec.ts` (`npm run test:perf`) keeps them from regressing.
- The old Parcel `alias` of `react-dom` to `react-dom/profiling` was dropped: nothing in the
  examples uses the `<React.Profiler>` API. (Several examples visualise re-renders by giving each
  render a random background colour, which needs no special build.) `vite.config.ts` documents how
  to switch the profiling build back on if it is ever wanted.

### Adding a new example

1. Create `examples/MyExample.tsx`, importing the library from `"../../src"` and wrapping the
   form in `<DEBUG_FormWrapper form={form}>`.
2. Add `MyExample: html_MyExample` (plus the matching `?raw` import) to `exampleSources.ts`.
   The highlighting and the display rewrites happen in `vite.config.ts`, there is nothing to run.
3. Register it in the `examples.basic` / `examples.advanced` array in `index.tsx`.
4. Give every interactive element a `data-testid` following the scheme below.

## `data-testid` scheme

E2E tests (Playwright) target elements by `data-testid`. `<ExampleName>` is always the exact
example component / file name, e.g. `SyncValidations` — the same string used as the section
anchor `id`.

| Pattern | Element |
| --- | --- |
| `<ExampleName>-<fieldName>-input` | the `<input>` / `<textarea>` / `<select>` for that field |
| `<ExampleName>-<fieldName>-errors` | the per-field error container (`.input-error`) |
| `<ExampleName>-submit` | the form's submit button |
| `<ExampleName>-result` | submit outcome — `"form is valid"` / `"form is invalid"`, empty before the first submit |
| `<ExampleName>-errors` | form-level (all fields) error summary, where an example has one |
| `<ExampleName>-state` | the JSON dump of the live form state rendered by `DEBUG_FormWrapper` — `{ fields: { <name>: { value, errors, isValidating, isValidated } }, isValidating, isValid, isValidated }` (everything `useFormio` returns minus the internal `__dangerous` key; `useCombineFormio` results nest the sub-forms under `forms`) |
| `<ExampleName>-code` | the highlighted source snippet |
| `<ExampleName>-heading` | the `<h3>` heading (also carries `id="<ExampleName>"`) |
| `<ExampleName>-github-link` | link to the example file on GitHub |
| `<ExampleName>-toggle-code` | "show/hide example source code" button (narrow viewports only) |

Example-specific extras, same prefix convention:

| Test id | Element |
| --- | --- |
| `AsyncValidations-<fieldName>-validate` | per-field "validate" button |
| `DebouncedInput-<fieldName>-set-hello` | "set text1 to HELLO" button |
| `DynamicForms-add-form` | "add form" button |
| `DynamicForms-<formKey>-<fieldName>-input` / `-errors` | fields of the n-th dynamic sub-form (`formKey` is `1` and `2` initially) |
| `DynamicForms-<formKey>-move-up` / `-move-down` / `-delete` | dynamic sub-form controls |
| `ThrottledCallToServer-search-input` | search input |
| `ThrottledCallToServer-loading` | "(loading)" indicator |
| `ThrottledCallToServer-result` | `<ul>` of results |
| `ThrottledCallToServer-calls-count` | "you did: N calls to server" |

Page-level ids:

| Test id | Element |
| --- | --- |
| `app` | app root |
| `site-header` | top navbar |
| `npm-link`, `github-link` | navbar links |
| `intro`, `installation`, `examples-toc` | intro / installation / table-of-contents blocks (also carry `id="intro"`, `id="installation"`, `id="examples"`) |
| `toc-<ExampleName>` | table-of-contents link for an example |
| `example-<ExampleName>` | the `<section>` wrapping one example (also carries `data-example="<ExampleName>"`) |

### Stable section ids

Each example section is `<section data-testid="example-<Name>" data-example="<Name>">` and its
heading carries `id="<Name>"`, so `#<Name>` deep links work. The ids are:

**basic** — `SyncValidations`, `FieldMetadata`, `AsyncValidations`, `InputConstrains`,
`CrossValidations`, `RevertToInitState`, `UseCombineFormioExample`, `LifecycleHooks`,
`SyncSetValuesBasedOnPrevValue`, `OnTouchValidation`, `UncontrolledInput`

**advanced** — `StableMethodPointers`, `DebouncedInput`, `ThrottledCallToServer`,
`OptimizedObjectRecreating`, `AdvancedFieldMetadataValidations`, `CustomFormSchemaFramework`,
`DynamicForms`

### Notes for test authors

- Submitting no longer opens a native `alert()`; assert on `<ExampleName>-result` instead.
- The code snippet column is only rendered on viewports wider than 1200px. Below that the source
  is behind the `<ExampleName>-toggle-code` button, so set an explicit viewport width in tests
  that touch snippets.
- `RevertToInitState` has no `-result` (its submit reverts the form instead of validating) and
  `ThrottledCallToServer` has no submit button.
- `AsyncValidations` validators fail randomly by design — do not assert a specific error there.
- The state dump carries an `isValidated` key, per field *and* at form level (where it means
  "every field is validated"), next to `isValid` / `isValidating`. It starts `false`, is set by
  `validate()`, and is reset back to `false` by `set()` on that field, by `clearErrors()` and by
  `revertToInitState()`. Note that `isValid` is `true` before anything has been validated — a
  spec that wants "this form has been checked and is fine" has to assert `isValidated` too.

## E2E tests

The `data-testid` scheme above exists for the Playwright suite in `e2e/`. Because the docs app
imports the library from `../src`, these tests exercise the **real library code**, not a build.

```bash
cd example
npm install
npx playwright install chromium   # once, downloads the bundled browser
npx playwright install chrome     # once, if you want the real Chrome project too
npm run test:e2e                  # headless, all specs, bundled chromium
npm run test:e2e:chrome           # the same suite in the real Google Chrome install
npm run test:e2e:all              # both browser projects
npm run test:perf                 # only the @perf CPU budget spec (chromium)
npm run test:e2e:ui               # interactive Playwright UI mode
npx playwright test dynamic-forms # one spec
npx playwright test --headed --debug
```

`playwright.config.ts` starts the app itself (`vite build && vite preview --port 1234
--strictPort`) and reuses an already running server outside CI, so `npm run dev` in another
terminal is picked up automatically. The build takes well under a second and a static preview
server behaves far more predictably under `fullyParallel` than an on-demand dev transform.
Two browser projects — `chromium` (playwright's bundled build, the default) and `chrome`
(`channel: "chrome"`, the real Google Chrome install) — `retries: 2` on CI, trace on first retry,
viewport pinned to 1400x900 so the `showCodeRight` (> 1200px) layout is deterministic. The
`@perf` spec is `grepInvert`ed out of the `chrome` project: a real Chrome profile brings
extensions and a warm renderer, which makes its CPU numbers far noisier than the budgets in
`e2e/perf.spec.ts` were calibrated for.

### Layout

| File | Covers |
| --- | --- |
| `e2e/helpers.ts` | the `Example` locator facade over the `data-testid` scheme, form-state polling, console collectors |
| `e2e/smoke.spec.ts` | page loads with no console errors / uncaught exceptions, all 18 sections, TOC, anchors, snippets, GitHub links |
| `e2e/<example-name>.spec.ts` | one spec per example, named after it (`sync-validations.spec.ts`, `dynamic-forms.spec.ts`, …) |
| `e2e/perf.spec.ts` | the `@perf` CPU budget: load script/task time, long tasks, the cost of 20 keystrokes, the memoisation proof, and the gzipped bundle size — all under a 4x CPU throttle |

Every spec starts with a comment quoting the validators / constraints of the example it covers, so
the expected messages in the assertions can be checked against the source without opening it.

### Conventions

- Assert through `expect(locator).toHaveText/toHaveValue/toBeDisabled` so Playwright auto-waits.
  The only fixed waits are the ones the examples themselves impose (the 500 ms debounce, the
  1000 ms throttle, the 200/1000 ms async validators) and they are named constants in the spec.
- Assert on rendered text where the example renders one, and on the `<ExampleName>-state` JSON
  (`Example#state()` / `Example#fieldState()`) where the interesting change is in the form state
  rather than on screen (debounce, uncontrolled input, `shouldChangeValue` rejections).
- The examples that visualise re-renders with a random background colour
  (`StableMethodPointers`, `OptimizedObjectRecreating`) are asserted through
  `inputBackgroundColor()`: the colour of the *edited* field has to change and the colour of the
  memoized sibling must not. That is a direct assertion that `useFormio` hands out stable
  `set` / `validate` pointers and keeps the empty `errors` array pointer.
- `AsyncValidations` fails randomly by design, so its result is only matched against
  `/^form is (valid|invalid)$/`; what is asserted precisely there is `isValidating`.
- `example/index.tsx` renders inside `<React.StrictMode>`. That used to be impossible: `afterSet`
  was scheduled from inside a `setState` updater, which StrictMode double-invokes, so the hooks
  would have fired twice per `set`. After the store refactor `useFormio` keeps its state outside
  React (`useStore` / `useSyncExternalStore`) and `set()` applies the write and fires `afterSet`
  synchronously, exactly once — the `LifecycleHooks` spec asserting "exactly once per `set`" now
  holds *with* StrictMode on. Note that the e2e suite runs the production build, where StrictMode
  does not double-invoke anything; `npm run dev` is what actually exercises it.

### Fixed: the first submit of "Dynamic forms"

`e2e/dynamic-forms.spec.ts` used to carry a `test.fail()` for a real defect:

> **The very first submit of "Dynamic forms" always reported "form is valid"**, even with every
> required field empty. `useCombineFormio(...)` is built during the *parent* render from the
> sub-form registry, but each sub-form registers itself from its own `useEffect` — and the
> registry was a `useRef`, so registering never re-rendered the parent. The first render therefore
> combined an empty set of forms, and validating zero forms is vacuously valid
> (`[].every(i => i) === true`). Only the second submit worked, because `setResult` had
> re-rendered the parent by then.

The fix is in `examples/DynamicForms.tsx`: the registry lives in `useState` (holding each
sub-form's *stable ref*, so the parent still reads the latest `isValid` / `isValidating` during
its render). Child effects run before the parent's, so registration re-renders the parent with
every sub-form before the first paint. `useCombineFormio` itself was not changed — reporting an
empty set of forms as valid is correct on its own, the defect was the registration pattern.

The `test.fail()` and its companion "documents the current behaviour" test are gone; the spec now
asserts the first submit reports the form invalid.
